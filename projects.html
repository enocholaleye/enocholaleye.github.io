PROJECT 01 · E-COMMERCE ARCHITECTURE · KUBERNETES
NexaHub Simulation — E-Commerce Platform on Amazon EKS
Kubernetes · Microservices · Multi-tenancy · GitOps
</> View on GitHub ↗

A production Amazon EKS cluster simulating the infrastructure demands of a high-traffic multi-vendor e-commerce marketplace. Designed to solve the core scaling challenge that plagues growing platforms: all services scaling as one unit, even when only one service is under load. The architecture enables each of 11 microservices to scale independently based on its own metrics — solving both the cost and availability problem simultaneously.

Key Architecture Decisions
Horizontal Pod Autoscaler (HPA) configured per service — payments service scales to 50 pods independently while reviews service remains at 1–2 pods, eliminating the over-provisioning that causes unnecessary cost.
Namespace-based multi-tenancy with Kubernetes Resource Quotas: premium namespaces get guaranteed CPU and memory allocation; standard namespaces operate on best-effort with enforced limits.
GitOps CI/CD pipeline: code push → GitHub Actions → Docker build → ECR push → Helm deploy to EKS, full rollout under 8 minutes with zero manual steps and full audit trail.
Helm charts written to be portable to GKE unchanged — workload portability as a first-class design constraint, enabling a future multi-cloud strategy without re-engineering application manifests.
Cluster Autoscaler provisions new worker nodes automatically under sustained load; Spot instance node group for burst capacity at 60% cost reduction versus On-Demand.
External Secrets Operator bridges AWS Secrets Manager to Kubernetes Secrets — credential rotation in Secrets Manager propagates to the cluster automatically, zero hardcoded secrets anywhere.

PROJECT 02 · FINTECH · CBN COMPLIANCE ARCHITECTURE
VaultEdge Simulation — CBN-Regulated Digital Banking Infrastructure
ECS Fargate · Defence-in-Depth Security · Aurora Multi-AZ
</> View on GitHub ↗

Production-grade, CBN-compliant AWS infrastructure modelled on the architecture required by a licensed digital bank. Designed to the security and availability standards of a strict central bank regulatory framework — defence-in-depth security, zero-downtime database operations, and a fully auditable infrastructure trail.

Key Architecture Decisions
Defence-in-depth security layering: WAF at the edge (blocks malicious traffic before it reaches the application), GuardDuty for continuous ML-powered threat detection, KMS encryption at rest and in transit across all data stores.
AWS Secrets Manager with automatic rotation — zero hardcoded credentials anywhere in the infrastructure. Database passwords, API keys, and service credentials all managed and rotated programmatically.
AWS Security Hub aggregates findings from GuardDuty, Config, and Inspector into a single compliance posture dashboard — providing the continuous monitoring evidence required for CBN regulatory review.
ECS Fargate for containerised microservices: serverless compute — AWS manages underlying nodes, eliminating a full layer of operational overhead while maintaining full container control.
Aurora Multi-AZ with automatic failover — in the event of a primary instance failure, standby promotes in under 30 seconds, meeting the zero-downtime availability requirements of a core banking API.
Full infrastructure provisioned as Terraform code — entire environment reproducible from a single command, making disaster recovery and environment cloning (dev → staging → prod) fully automated.

PROJECT 03 · HEALTHCARE · NDPA COMPLIANCE ARCHITECTURE
MediCore Simulation — NDPA-Compliant Healthcare EHR Infrastructure
Auto Scaling · Multi-AZ RDS · Systems Manager · No-SSH Architecture
</> View on GitHub ↗

Secure, NDPA-compliant AWS environment modelled on the infrastructure requirements of a multi-site hospital Electronic Health Record platform. Patient record systems have zero tolerance for availability failures — this architecture is designed around that constraint, with compliance controls that satisfy data protection regulations (NDPA) for sensitive health data.

Key Architecture Decisions
Auto Scaling Groups ensure the application layer scales automatically under peak clinical load (morning ward rounds, end-of-day data entry surges) and scales back down during off-peak hours to control costs.
RDS MySQL Multi-AZ with automated backups and point-in-time recovery — patient record data is never at risk from a single instance failure. Standby instance promotes automatically with zero data loss.
AWS Systems Manager Session Manager replaces SSH entirely — no exposed port 22, no key management overhead, full session logging to CloudTrail for compliance. Every access to every instance is audited.
ACM-managed SSL/TLS certificates with automatic renewal — no certificate expiry risk, no manual rotation. All patient data in transit is encrypted end-to-end.
Secrets Manager for database credentials and API keys with automatic rotation — no static credentials that could be harvested if a server is compromised.
CloudTrail logging across all regions captures every API call — providing the audit evidence required for NDPA compliance review and breach notification procedures.

PROJECT 04 · LOGISTICS · CLOUD MIGRATION ARCHITECTURE
SwiftHaul Simulation — Emergency Cloud Migration Architecture
Cloud Migration · High Availability · Zero Data Loss · Terraform
</> View on GitHub ↗

An emergency migration architecture modelled on the scenario of a logistics company whose on-premises infrastructure is failing — systems degrading, operations at risk. This project demonstrates the decision-making, architecture design, and execution required to move a business off dying infrastructure onto AWS quickly, safely, and with zero data loss. The most important skill tested here is not technical depth but operational judgement under pressure.

Key Architecture Decisions
VPC design prioritises separation of concerns from day one: public subnets for ALB and NAT Gateway, private subnets for application and database layers — no database ever exposed to the internet.
ALB with health checks ensures traffic is only routed to healthy instances — if an EC2 instance fails during migration or operation, the ALB removes it from rotation automatically.
RDS MySQL with automated backups and Multi-AZ configured from the start — data migration validated against RDS before cutting over, ensuring zero data loss is verifiable before the old system is decommissioned.
S3 for static assets and document storage — removes file system dependencies from EC2 instances, making the application layer stateless and therefore horizontally scalable and resilient to instance failure.
CloudWatch alarms and SNS notifications configured before go-live — operations team receives immediate alerts on CPU, memory, RDS connections, and ALB error rates from day one.
Full Terraform codebase from day one — if any component fails post-migration, it can be destroyed and reprovisioned in minutes without manual intervention.
